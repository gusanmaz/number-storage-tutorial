Giving letters numbers

Computers do not know letters; they only store numbers. Every letter on this page is a number someone agreed on. The story of that agreement also explains where garbled text like “cafÃ©” comes from.

§ 7.1There is no such thing as a letter

In Chapter 1 we saw that the same bit pattern can be a number, a color or a letter. To store text, all we need is a table: a list that gives every character a number and that everyone uses the same way. The sender writes 65 for “A”, the receiver sees 65 and draws an “A”. In between, the computer carries nothing but 65.

§ 7.2ASCII: the 7-bit agreement

In 1963 the American standards body published ASCII (American Standard Code for Information Interchange). 7 bits, so 128 numbers: 33 control codes, the space, digits, upper and lower case English letters and punctuation. Every character encoding you use today still contains ASCII as its first 128 numbers.

The table is not arranged at random. The columns are split by the top 3 bits of the number, so characters of the same kind gather in the same columns. Tap a cell and look for the patterns.

Three patterns in the table show how thoughtful ASCII’s designers were:

  • Digits start at 0x30. The low 4 bits are the digit itself: '7' = 0x37. To turn a digit character into a number you just take the low nibble (or subtract 48).
  • Letters start at 0x41 and 0x61; the low 5 bits are the letter’s position in the alphabet: A = 1, B = 2…
  • Upper and lower case differ by exactly 32, which is a single bit. Try it below.

97 − 65 = 32 and 55 − 48 = 7. The first converts case and the second turns a digit character into a number, each in a single operation. In C, writing c - '0' means “the value of this digit character”.

§ 7.3Invisible characters

ASCII’s first 32 codes and 127 are not letters but commands. ASCII was designed in the age of machines that printed text, teleprinters. These codes gave the machine orders like “ring the bell”, “feed the paper one line”, “move the head back to the start of the line”. The teleprinter below understands some of them.

This split lives on today: Windows stores line endings as CR LF (0D 0A), Linux and macOS as just LF (0A). That is why lines sometimes merge or show stray ^M marks when you open a file on another system.

To write these invisible characters in programming languages we use escape sequences: a letter after a backslash means “read this not as a plain letter but as a special code”. \n looks like two characters but is a single byte in memory: 0A.

print(ord("A"), chr(97))          # 65 a
print("name\tsurname\nAda\tLovelace")  # tab and newline
print(len("\n"))                  # 1  (a single character!)
print(repr("a\tb"))               # 'a\tb'  makes escapes visible
print("\x41B")               # AB  (characters by hex)
print("\a")                       # beeps in some terminals!
print("\x1b[31mred\x1b[0m")       # terminal color via ESC

§ 7.4A string in memory

A string is nothing but bytes sitting side by side in memory. But there is a problem: memory is one long strip of bytes and we need to know where the text ends. There are two classic solutions. C puts a NUL (00) at the end; Pascal and modern languages store the length at the start or alongside.

The terminator approach has another cost: to find a string’s length, C’s strlen has to count every byte until it finds the NUL. Python and JavaScript, which store the length separately, know it instantly, and their strings can even contain NUL.

§ 7.5When 128 is not enough: code pages

ASCII has no é, ñ, ü, ç or ş. Since a byte is 8 bits, the unused 8th bit could buy 128 more numbers. Everyone did just that, but everyone differently. ISO-8859-1 (Latin-1) for Western Europe, ISO-8859-9 (Latin-5) and Windows-1254 for Turkish, KOI8-R for Russian… These are called code pages. The same byte is a different letter depending on which code page reads it.

This is why Turkish e-mails in the 1990s arrived as “Ýyi günler, þimdi…”: the sender’s computer wrote in Latin-5 while the receiver’s read in Latin-1. The bytes arrived perfectly; what was broken was the agreement.

§ 7.6Unicode: one number per character

To end this chaos, Unicode appeared in 1991. The idea is simple: give every character of every writing system in the world a single, permanent number. That number is called a code point and is written in hex after U+: A = U+0041, ş = U+015F, € = U+20AC, 😀 = U+1F600.

Unicode has 1,114,112 slots (U+0000 … U+10FFFF); about 150,000 are filled today: Latin, Arabic, Chinese and Indic scripts, mathematical symbols, Egyptian hieroglyphs and emoji. Paste any text below and open it up:

Character ≠ code point ≠ byteWhat we see as a “letter” (Unicode calls it a grapheme) corresponds to one or more code points. Each code point takes one or more bytes depending on the encoding. So “how many characters is this text?” can have three different answers.

§ 7.7UTF-8: pouring the number into bytes

Unicode gives the number; the encoding decides how that number is stored in memory. The simplest way is 4 bytes per character (UTF-32), but that makes an English text four times bigger. UTF-8, sketched by Ken Thompson and Rob Pike on a placemat in a diner in 1992, is used today by more than 98% of web pages. The idea: small numbers take few bytes, big ones more.

The code point’s bits are poured into the template’s xs from right to left. Pick a character and follow along step by step:

This design has four lovely consequences:

  • ASCII compatible. The first 128 characters stay single bytes; every old English file is already valid UTF-8.
  • Self-synchronizing. Even if you start reading at a random byte, you can skip the ones starting with 10 and find the start of the next character.
  • No fake NULs or “/”. All bytes of a multi-byte character are above 127, so C’s NUL-terminated strings and file paths are not broken.
  • Sorting is preserved. Sorting the bytes gives the same order as sorting the code points.

UTF-16 stores characters in 2 or 4 bytes and lives inside Windows, Java and JavaScript. Code points above U+FFFF are split into two 16-bit pieces, a surrogate pair. Because JavaScript’s length counts these 16-bit pieces, surprises follow:

"ş".length                     // 1
"😀".length                    // 2  ← two UTF-16 pieces
[..."😀"].length               // 1  ← number of code points
"😀".codePointAt(0).toString(16) // "1f600"
new TextEncoder().encode("ş")   // Uint8Array [197, 159]  (UTF-8: C5 9F)
"ş" === "ş"               // true
"\u{1F600}"                    // "😀"

len("ş")                 # 1
len("😀")                # 1  ← Python counts code points
"ş".encode("utf-8")      # b'\xc5\x9f'
len("😀".encode())       # 4  ← number of bytes
hex(ord("😀"))           # '0x1f600'
"\N{EURO SIGN}"          # '€'
b"\xc5\x9f".decode()     # 'ş'

§ 7.8Anatomy of garbled text

The Japanese even have a name for it: mojibake, “character transformation”. If a program reads text saved as UTF-8 thinking it is Windows-1252 (the Windows cousin of Latin-1), every multi-byte character turns into two or three meaningless symbols. Try your own text:

A text file does not say which encoding it was written in. That is why we write <meta charset="utf-8"> in HTML and open(name, encoding="utf-8") in Python. Always state the encoding explicitly, and choose UTF-8.

A special trap: the Turkish IIn most languages the lower case of “I” is “i”. In Turkish, however, I ↔ ı and İ ↔ i. A program that ignores the language lowercases “IŞIK” to “işik”; in Java, "title".toUpperCase() on a computer set to Turkish returns “TİTLE”, breaking code that looks for an English keyword. Developers call this the “Turkish I problem”. The fix: locale-aware functions (toLocaleUpperCase('tr')) where language matters, and locale-independent ones for identifiers.
