Floating Point: IEEE 754

How do numbers like 3.14 or 0.1 live in memory? In this chapter you will take floating-point numbers apart piece by piece and solve programming’s most famous oddity — 0.1 + 0.2 ≠ 0.3 — yourself.

  • read the sign, exponent and mantissa of a float;
  • explain why 0.1 + 0.2 prints 0.30000000000000004;
  • know the precision limits of floats, their special values (∞, NaN) and how to compare them properly.

Binary fractions first

In decimal, the digits after the point are worth 1/10, 1/100, 1/1000. Binary works the same way, just with base 2:

12¹ = 2
12⁰ = 1
.
12⁻¹ = ½
02⁻² = ¼
12⁻³ = ⅛

11.1012 = 2 + 1 + 0.5 + 0.125 = 3.625

To convert a decimal fraction to binary we use multiply by 2, take the integer part: multiply the fraction by 2; if the result is 1 or more, that digit is 1 (and we subtract the 1), otherwise it is 0. Repeat until the fraction becomes zero.

0.1 is infinite in binary

In decimal, 1/3 = 0.3333… goes on forever because 3 does not divide 10. In binary, every fraction whose denominator is not a power of 2 repeats forever: 1/10, 1/5, 1/3… So 0.1 can never be stored exactly; only a value very close to it is stored.

Binary scientific notation

In physics we write very large or small numbers in scientific notation: 602,200,000,000,000,000,000,000 = 6.022 × 10²³. We move the point and adjust the exponent. Computers do the same in binary — the point “floats”, hence floating point:

110.11₂ = 1.1011₂ × 2² Move the point just to the right of the first 1. Each move left adds 1 to the exponent, each move right subtracts 1.

A normalized binary number always starts with 1.xxxx (except zero). We will use that to save a bit in a moment.

IEEE 754: three fields

A 32-bit float stores the parts of scientific notation in three fields:

Sign1 bit0 = +, 1 = −
Exponent8 bitsreal exponent + 127
Mantissa (fraction)23 bitsthe bits after the point
value = (−1)sign × 1.mantissa₂ × 2(exponent − 127)

Why “+127” (bias)?

The exponent can be negative (for small numbers like 0.001). Instead of two’s complement, 127 is added before storing; so the 8-bit field holds exponents from −126 to +127, and floats can be compared just like unsigned integers.

The hidden bit (implicit 1)

Every normalized number starts with 1., so there is no need to store that 1! Only the bits after the point are kept. 23 bits of storage give 24 bits of precision.

Why isn’t 0.1 + 0.2 equal to 0.3?

JavaScript and Python use 64-bit doubles by default (52-bit mantissa). Even so, 0.1 cannot be stored exactly. The stored values of 0.1 and 0.2 are slightly too big, while the stored value of 0.3 is slightly too small. The sum lands not on 0.3’s representation but on its neighbour:

What is really stored?

console.log(0.1 + 0.2);              // 0.30000000000000004
console.log(0.1 + 0.2 === 0.3);      // false

// Correct comparison: "close enough?"
const close = (x, y, tol = 1e-9) => Math.abs(x - y) < tol;
console.log(close(0.1 + 0.2, 0.3));  // true

// For money: use integer cents
const price = 1999;                  // $19.99 → 1999 cents
console.log((price * 3) / 100);      // 59.97

print(0.1 + 0.2)                 # 0.30000000000000004
print(0.1 + 0.2 == 0.3)          # False

import math
print(math.isclose(0.1 + 0.2, 0.3))   # True

# For money and exact decimal arithmetic, use Decimal:
from decimal import Decimal
print(Decimal("0.1") + Decimal("0.2"))   # 0.3

# See the exact stored value:
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625
Common mistake: comparing floats with ==

Never compare two computed floats with ==; check whether their difference is within a small tolerance. Don’t use floats for money: use integer cents or Decimal.

Precision is limited: there are gaps between numbers

Because the mantissa has a fixed number of bits, floats cover the number line not with equal spacing but with gaps that grow with the exponent. Near 1 the gap between neighbouring floats is tiny; for large numbers it grows. In a 32-bit float, odd numbers above 2²⁴ = 16,777,216 can no longer be represented!

In the real world: the Patriot missile (1991)

During the Gulf War a Patriot system counted time in steps of 0.1 seconds and stored 0.1 as a 24-bit fixed-point number. The tiny rounding error at each step added up to about 0.34 seconds after 100 hours. An incoming missile travels more than 500 metres in that time, and the target was missed.

Summary

  • Digits after the binary point are worth ½, ¼, ⅛…; fractions whose denominator isn’t a power of 2 (like 0.1) repeat forever.
  • IEEE 754 float = sign (1) + exponent (8, bias 127) + mantissa (23). The leading 1 is not stored.
  • Value = (−1)ˢ × 1.mantissa × 2^(exponent−127).
  • Floats are approximations: use tolerant comparisons instead of ==, and integers/Decimal for money.
  • The gap between representable values grows with magnitude; ∞ and NaN are special bit patterns.

0.375 = 3/8; the denominator is a power of 2 → 0.011₂. The others repeat forever in binary.

Why isn’t the leading 1 of the mantissa stored?

  • To make the number positive
  • It is always 1 for normalized numbers, so a bit is saved
  • To compute the bias
  • It is stored, just not shown
Every normalized number looks like 1.xxx; storing something you already know would be wasteful.
