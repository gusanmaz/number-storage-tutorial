Chapter 6

Where the point goes: fractions

How do we write 3.14 or 0.1 with lamps? The answer leads to programming’s most famous oddity: as far as the computer is concerned, 0.1 + 0.2 is not 0.3.

Reading: ~35 minBefore: Chapters 2 and 5

§ 6.1There are boxes right of the point too

In decimal, the digits right of the point are worth a tenth, a hundredth, a thousandth. We can extend the exploding dots machine to the right as well: each box is worth one base-th of the box to its left. In binary that means the boxes right of the point are a half, a quarter, an eighth… Like cutting a strip in half again and again.

This tells us something both beautiful and unsettling. Fractions like ½, ¾ and ⅝ can be written exactly with a few bits. But 0.1? No combination of lamps paints exactly a tenth of the strip. Let’s prove it.

§ 6.2Why 0.1 never ends in binary

To convert a fraction to binary, keep multiplying it by 2: if the result reaches 1, that digit is 1 (and we drop the 1); if not, it is 0. We stop when the fraction reaches zero. Try 0.625 first, then 0.1.

Decimal has the same problem: 1/3 = 0.3333… never ends, because 3 does not divide 10. The binary rule is similar: any fraction whose denominator (after reducing) is not a power of 2 repeats forever in binary. 1/10 has a 5 in its denominator, so none of everyday numbers like 0.1, 0.2, 0.3 can be stored exactly in a computer. What gets stored is a value very close to it.

§ 6.3Pinning the point down

The simplest solution is to fix the position of the point in advance: of 8 bits, 4 for the integer part and 4 for the fraction. This is called fixed point. The values are evenly spaced on the number line.

Fixed point is still used today. Working in cents (1999 cents instead of $19.99) is a kind of fixed point and avoids rounding surprises. But fixed point cannot write 0.1 exactly either, and small errors can add up:

In real lifeIn the 1991 Gulf War a Patriot missile defense system counted time in steps of 0.1 seconds and stored 0.1 as a 24-bit fixed-point number. The tiny error at each step grew to about 0.34 seconds after 100 hours; in that time a missile travels more than half a kilometer. The incoming missile was not intercepted.

§ 6.4Letting the point float

To write very large and very small numbers at the same time, physics uses scientific notation: Avogadro’s number is 6.022 × 10²³, an electron’s mass 9.1 × 10⁻³¹ kg. The digits of the number (6.022) and its size (10²³) are written separately, and the point “floats” according to the exponent.

The computer does the same in binary: 110.11 = 1.1011 × 2². We move the point to just after the first 1 and store the shift as an exponent. Every number except zero then starts with 1.xxxx.

number = (sign) × 1.mantissa × 2exponent

This picture captures the essence of floating point: relative precision is constant, absolute precision is not. We move in very fine steps for small numbers and coarse steps for big ones. That is exactly what science wants: we do not need a planet’s distance to the millimeter, but we do need an atom’s size.

§ 6.5The real format: IEEE 754

The IEEE 754 standard, published in 1985, is the format nearly every processor uses today. A 32-bit float is split into 1 sign bit, 8 exponent bits and 23 mantissa bits. A 64-bit double has 11 exponent bits and 52 mantissa bits. JavaScript numbers and Python’s float are doubles.

Why is the exponent stored “+127”? The exponent can be negative. Instead of two’s complement a fixed number (the bias) is added, so 8 bits hold exponents from −126 to +127 and two floats can be compared as easily as unsigned integers.

The hidden bit. Since every normalized number starts with 1., there is no need to store that 1. Only the part after the point goes into the mantissa; 23 bits of space give 24 bits of precision. A free bit!

§ 6.6Why 0.1 + 0.2 isn’t 0.3

Now we have everything we need to solve the mystery. None of 0.1, 0.2 and 0.3 can be stored exactly as a double. The stored 0.1 and 0.2 are slightly too big, the stored 0.3 slightly too small. The sum lands not on the double that represents 0.3 but on the one right next to it.

print(0.1 + 0.2 == 0.3)               # False

import math
print(math.isclose(0.1 + 0.2, 0.3))   # True: "close enough?"

from decimal import Decimal           # for money and exact decimal math
print(Decimal("0.1") + Decimal("0.2"))   # 0.3
print(Decimal(0.1))                   # the value actually stored:
# 0.1000000000000000055511151231257827021181583404541015625

console.log(0.1 + 0.2 === 0.3);        // false

const close = (x, y, tol = 1e-9) => Math.abs(x - y) < tol;
console.log(close(0.1 + 0.2, 0.3));    // true

// for money, use integer cents:
const price = 1999;                    // $19.99
console.log(price * 3 / 100);          // 59.97

Never compare two floating-point numbers with ==: check whether their difference is below a small tolerance. Do money calculations with integer cents or decimal types (Decimal in Python).

§ 6.7The limits of precision and special values

The gaps we saw in the toy float exist in the real float too, just smaller. In a 32-bit float, odd numbers can no longer be written after 224 = 16,777,216: becomes when converted to float. For doubles the same limit is 253 ≈ 9 × 1015.

When the exponent bits are all 0 or all 1, special meanings kick in. Try the “0”, “−0”, “∞” and “NaN” buttons in the lab:

  • ±0: Yes, there is a negative zero too (but 0 === -0 is true).
  • ±∞: 1 / 0 or a result that is too big. The program does not crash; it carries on with infinity.
  • NaN (“not a number”): 0 / 0, Math.sqrt(-1). NaN equals nothing, not even itself: NaN === NaN is false.
  • Subnormal numbers: When the exponent bits are zero the hidden bit is taken as 0; this is how numbers very close to zero are written.

  • 0.375
  • 0.1
  • 0.2
  • 1/3
0.375 = 3/8; the denominator is a power of 2 → 0.0112.

How does the gap between neighboring floating-point values change?

  • It is the same everywhere
  • It grows near zero
  • It is random
  • It grows as the numbers grow
Every power-of-two interval holds the same number of values; bigger intervals mean bigger gaps.

Why isn’t the leading 1 of the mantissa stored?

  • To make the number positive
  • Because it is always 1 in normalized numbers
  • To compute the exponent
  • It is stored, just not shown
Storing something already known is a waste; that bit goes to precision instead.

What does NaN === NaN give in JavaScript?

  • true
  • An error
  • false
  • NaN
By IEEE 754, NaN equals nothing. To test for it use Number.isNaN(x).
